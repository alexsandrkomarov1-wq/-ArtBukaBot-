**Версия:** 1.1  
**Дата фиксации:** 27 ноября 2026  
**Рабочая ветка:** `core-backend-foundation`  
**Репозиторий:** `alexsandrkomarov1-wq/-ArtBukaBot-`  
**Назначение:** единый реестр внутренних модулей, внешних интеграций, совместимости с облачными хранилищами и возможностей Supabase.

> Этот документ описывает целевую архитектуру и подтверждённое состояние кода. Наличие строки в реестре не означает, что сервис уже авторизован, развёрнут или прошёл сквозной тест.

## 1. Правила реестра

### Статусы

| Статус | Значение |
|---|---|
| `LIVE_VERIFIED` | Подключение реально выполнено; проверены авторизация, запись, чтение, целостность и обработка отказа |
| `IMPLEMENTED_LOCAL` | Код работает локально/в тестах, но нет подтверждённого рабочего подключения в production |
| `ADAPTER_CONFIGURED` | Есть адаптер или конфигурационная поддержка; реальные учётные данные и проверка провайдера отсутствуют |
| `DESIGNED` | Архитектура и контракт описаны; реализация не завершена |
| `RESEARCH` | Требуется проверить официальный API, OAuth, квоты и условия автоматизации |
| `BLOCKED` | Нельзя внедрять до устранения указанного блокера |
| `NOT_CONNECTED` | Нет действующего подключения |

Запрещено повышать статус без проверяемого результата. «Кнопка есть», «SDK установлен» и «тест прошёл с mock-объектом» не являются доказательством реального подключения.

### Обязательные поля записи

Каждый будущий плагин/адаптер должен иметь: уникальный `plugin_id`, название и версию, тип, владельца/источник, предоставляемые возможности, зависимости, разрешения, используемые сущности, место хранения секретов, health-check, тесты, текущий статус, дату последней проверки и план отключения/отката.

### Общий контракт модулей

- Единые постоянные идентификаторы: PERSON-ID, EVENT-ID, PLACE-ID, MATERIAL-ID.
- Каталог KOMAROVA_CORE является источником истины для метаданных и связей. Облачный провайдер — только место хранения байтов/реплики.
- Оригинал неизменяем. Любая улучшенная, преобразованная или восстановленная версия — отдельный материал с новым MATERIAL-ID и ссылкой на оригинал.
- Модули обращаются к каталогу через API/сервисный контракт, а не создают собственные несвязанные копии реестра.
- В публичный GitHub Pages не передаются семейные оригиналы, приватные метаданные, токены и секреты.

## 3. Реестр совместимости с облачными хранилищами

Проверка должна охватывать не только OAuth, но и выбор/создание приватной папки `KOMAROVA_CORE`, загрузку, чтение обратно, сверку SHA-256 и размера, повтор задания, паузу, отзыв доступа и восстановление.

| Provider ID | Провайдер | Тип/API | Текущее состояние | Следующий критерий допуска |
|---|---|---|---|---|
| `storage.local` | Private local storage | Локальный адаптер приватного backend | `IMPLEMENTED_LOCAL` — используется в разработке; не является production-хранилищем без постоянного диска и резервирования | Проверить развёртывание на постоянном томе, резервную копию и восстановление |
| `storage.s3` | S3-compatible | S3 API | `IMPLEMENTED_LOCAL` / базовая абстракция; фактический провайдер зависит от конфигурации | Сквозной тест на реальном приватном бакете |
| `storage.r2` | Cloudflare R2 | S3-compatible API | `ADAPTER_CONFIGURED` — конфигурация адаптера есть; аккаунт, бакет и реальные ключи не подтверждены | Приватный бакет, ограниченный токен, upload/read-back/SHA-256 и проверка тарификации |
| `storage.supabase` | Supabase Storage | Supabase Storage API | `DESIGNED` — клиент и SQL-заготовка есть; RLS, секреты, загрузка, чтение и восстановление не проверены | Отдельное разрешение на настройку существующего проекта, затем тесты политик и файлов |
| `storage.google-drive` | Google Drive | Google Drive API / OAuth 2.0 | `DESIGNED` / временный локальный OAuth-тест; не считать постоянным или production-подключением | После решения по инфраструктуре: серверный OAuth callback, минимальные scopes, upload/read-back и отзыв |
| `storage.onedrive` | Microsoft OneDrive | Microsoft Graph / OAuth 2.0 | `DESIGNED` | Проверить app registration, scopes, OAuth и тест приватной папки |
| `storage.yandex-disk` | Яндекс Диск | REST API / OAuth | `DESIGNED` | Проверить OAuth, API ограничения, загрузку, чтение и контроль целостности |
| `storage.dropbox` | Dropbox | Dropbox API / OAuth 2.0 | `RESEARCH` | Подтвердить scopes, refresh token, квоты и поведение API |
| `storage.pcloud` | pCloud | HTTP API / OAuth | `RESEARCH` | Проверить региональный API endpoint, OAuth и полный цикл файловых операций |
| `storage.mega` | MEGA | Официальный developer/API stack | `RESEARCH` | Подтвердить пригодность официального API/SDK для серверной автоматизации и условия использования |
| `storage.terabox` | TeraBox | API не подтверждён | `BLOCKED` | Не начинать интеграцию до подтверждения официального API, разрешённого способа авторизации и условий автоматизации |

**Важно о квотах:** бесплатные объёмы и лимиты не фиксируются как гарантированные свойства адаптера. Их нужно проверять по официальной странице тарифа в день подключения и хранить с датой проверки. Сторонний клиент для монтирования облака не доказывает наличие официального серверного API.

### Правила единого каталога и репликации

1. Один логический материал имеет один MATERIAL-ID и один неизменяемый Blob ID; репликация в несколько облаков не создаёт новые материалы.
2. Для каждой копии хранить provider key, внутренний location ID, непрозрачный remote object ID, размер, checksum, состояние и время последнего успешного чтения.
3. Состояния копии: `pending`, `available`, `paused`, `missing`, `integrity_error`, `revoked`.
4. Состояние `available` разрешено только после успешного чтения обратно и сверки контрольной суммы.
5. Сбой одного облака не останавливает другие провайдеры и не удаляет запись каталога.
6. Отключение аккаунта отзывает доступ и помечает местоположения как недоступные; удаление удалённых файлов — отдельная операция с явным подтверждением.
7. Импорт означает копирование. Исходный файл пользователя не перемещается и не удаляется.
8. Секреты и refresh tokens находятся только на сервере в защищённом хранилище; браузер, Git и публичный сайт их не получают.

## 4. Supabase: отдельный реестр возможностей и совместимости

**Существующий проект KOMAROVA_CORE:** `bcotusztvddzbnwefnrq`.  
**Режим на дату документа:** существующий проект сохраняется; никаких изменений конфигурации, пароля БД, таблиц, Storage, RLS или Edge Functions этим документом не выполняется.

Supabase — не «плагин облачного диска». Это backend-платформа, которую можно использовать как набор отдельных сервисов. Её функции должны быть подключены к архитектуре KOMAROVA_CORE через контролируемые адаптеры.

| Компонент Supabase | Возможная роль в KOMAROVA_CORE | Совместимость | Текущее состояние / ограничение |
|---|---|---|---|
| PostgreSQL Database | Метаданные каталога, PERSON/EVENT/PLACE/MATERIAL, связи, аудит | Высокая | Проект существует; таблицы и миграции не менять до отдельного разрешения |
| Supabase Auth | Аутентификация и внешние OAuth-провайдеры | Высокая | Не включать параллельно с текущей backend-auth без решения об одном источнике сессий и ролей |
| Supabase Storage | Приватные файлы и объекты медиатеки | Высокая, но не заменяет реестр копий | SQL/client заготовки есть; buckets, RLS и сквозной файловый тест не подтверждены |
| Row Level Security (RLS) | Разграничение семейных данных по пользователям и ролям | Обязательная защита при доступе через клиентские API | Политики не считать настроенными до аудита и тестов на разных ролях |
| Edge Functions | Короткие серверные API, webhook, интеграции и orchestration | Высокая для коротких задач | Не использовать как замену долгоживущему AI/media worker |
| Realtime | Обновление статусов загрузки, синхронизации и интерфейса | Высокая | Не настроено/не проверено для проекта |
| PostGIS | Географические точки, расстояния и маршруты | Возможная опция | Расширение не включать без проектирования схемы и отдельного разрешения |
| pgvector | Семантический поиск по описаниям и семейным материалам | Возможная опция | Не требуется для первого запуска; данные и модель доступа нужно спроектировать отдельно |
| pg_cron / Queues | Плановые задания и очереди | Возможная опция | Проверить доступность на текущем плане; тяжёлые медиа-задачи лучше выполнять отдельным worker |
| Management API / MCP | Управление проектом и диагностические операции | Административный интерфейс, не runtime-плагин сайта | Не выдавать доступ сайту; административные токены не помещать в браузер |

### Supabase Explorer из переданной ссылки

Переданная ссылка ведёт в Supabase Dashboard, раздел организаций, с параметром открытия Feature Preview Explorer:

`https://supabase.com/dashboard/organizations?featurePreviewModal=preview-explorer`

Explorer — предварительная версия рабочего пространства запросов: в нём можно исследовать SQL-данные и логи, а также сохранять исследования в Notebooks. Это инструмент управления/диагностики в Dashboard, а не плагин, который автоматически встраивается в сайт KOMAROVA_CORE, и не облачное хранилище файлов.

**Что это даст проекту после отдельного включения и проверки:**
- удобнее анализировать таблицы и журналы Supabase;
- сохранять повторяемые SQL- и log-исследования в Notebooks;
- диагностировать ошибки запросов и серверных функций;
- помогать сопровождению проекта, не создавая отдельную панель анализа логов.

**Чего это не сделает автоматически:**
- не подключит Supabase к GitHub Pages;
- не развернёт наш Python backend;
- не настроит приватные buckets и RLS;
- не подключит Google Drive/OneDrive/MEGA и другие облака;
- не перенесёт семейные файлы и не создаст архив;
- не включит Explorer в пользовательский интерфейс KOMAROVA_CORE.

Параметр ссылки запрашивает окно Feature Preview Explorer. Фактическая доступность и включение функции зависят от авторизованной сессии и состояния Dashboard. По одной ссылке нельзя подтвердить, что функция уже включена в организации пользователя.

## 6. Архитектура плагинов

Рекомендуемая граница:

- **UI plugin:** вкладка/панель интерфейса; не содержит секретов и не обращается к провайдеру напрямую.
- **Core service:** проверяет права пользователя, связывает действие с PERSON/EVENT/PLACE/MATERIAL и записывает аудит.
- **Provider adapter:** реализует общий контракт провайдера и преобразует операции в API конкретного сервиса.
- **Worker/queue:** выполняет повторяемые и длительные операции: копирование, сверку, сканирование и обработку медиа.
- **Registry:** хранит состояние плагина, версии, разрешения, зависимости, результаты health-check и тестов.

Минимальный контракт адаптера хранилища:
- `connect()` / `disconnect()`
- `health_check()`
- `list_objects()`
- `put_object()`
- `get_object()`
- `get_metadata()`
- `verify_object()`
- `pause_replication()` / `resume_replication()`

Удаление объекта не входит в автоматический сценарий синхронизации. Оно должно быть отдельной защищённой операцией.

## 9. План приёмки

Плагин или провайдер может получить `LIVE_VERIFIED` только после прохождения относящихся к нему проверок:

- установка/инициализация и проверка версии;
- минимальные разрешения и корректная авторизация;
- позитивный сценарий и отказ в доступе для неразрешённой роли;
- запись и чтение реального тестового объекта;
- совпадение SHA-256 и размера;
- повтор задания без дубликатов;
- обработка истёкшего/отозванного токена и сетевого сбоя;
- пауза, отключение и восстановление;
- отсутствие секретов в логах и клиентском коде;
- CI green и документированное доказательство теста.

**Итоговый принцип:** сначала совместимый и безопасный контракт, затем один адаптер, затем проверка на реальном сервисе. Одновременное подключение всех облаков и Supabase без backend, прав доступа и теста восстановления не допускается.

### 11.5 ИИ-летописец: рассказ о событии по видео и туристической прогулке

Вводится отдельный функциональный модуль `core.storyteller` — **ИИ-летописец / рассказчик событий и маршрутов**. Он не должен сочинять семейные факты. Его задача — собирать проверяемые сведения из материалов и предлагать человеку черновик рассказа.

| Подмодуль | Вход | Результат | Связи каталога |
|---|---|---|---|
| `story.video-analysis` | Видео, аудиодорожка, дата/место при наличии | Таймкоды, транскрипт, ключевые кадры, черновое описание сцен | Исходный MATERIAL-ID, производные кадры/транскрипт |
| `story.walk-analysis` | GPX/KML/GeoJSON, GPS-точки, фотографии, заметки и временная шкала | Хронология прогулки, остановки, точки интереса и черновой маршрут | PLACE-ID, EVENT-ID, MATERIAL-ID |
| `story.fact-check` | Извлечённые данные, подписи пользователя, источники | Список подтверждённых фактов, неизвестных полей и противоречий | Источники и журнал происхождения |
| `story.narrative` | Проверенные факты и выбранный стиль | Текст летописи, подписи к фото, аудиорассказ и субтитры | EVENT-ID, PLACE-ID и связанные материалы |
| `story.review` | Черновик ИИ | Подтверждение, исправление или отклонение человеком | Автор проверки, дата, версия и аудит |

**Сценарий по видео:** принять файл → проверить доступ и безопасность → получить технические метаданные → извлечь аудио/кадры → распознать речь и таймкоды → предложить описание сцен → связать только подтверждённые места/людей/события → показать черновик → получить подтверждение владельца/редактора → сохранить рассказ отдельным материалом.

**Сценарий туристической прогулки:** импортировать трек или разрешённые GPS-метаданные → сопоставить точки с картой → объединить остановки с фото, видео и заметками по времени → предложить последовательность посещений → сформировать рассказ о маршруте → дать человеку проверить географию и формулировки → сохранить маршрут и текст с PLACE-ID/EVENT-ID.

ИИ не должен определять личность человека на видео, объявлять неизвестную точку посещённым местом или выдавать догадку за исторический факт. Если GPS отсутствует или неточен, место помечается как предположение до ручного подтверждения. Все сгенерированные описания помечаются как AI draft до одобрения.

## 12. Матрица совместимости двух платформ KOMAROVA_CORE

Под «двумя платформами» понимаются две веб-поверхности одного проекта, а не два независимых архива. Они должны использовать общие идентификаторы и единый backend/API.

| Категория | Главный портал `/` | Облачная сеть `/cloud-network/` | Общий контракт |
|---|---|---|---|
| Photoshop и графика | Открытие/выбор фото, запуск обработки, сравнение ORIGINAL/DERIVED | Запись результата в каталог, выбор целевых облачных копий, checksum | MATERIAL-ID, версия, производная связь |
| Видеоплееры | Защищённый просмотр, субтитры, таймкоды | Хранение оригинала и производных потоков/файлов, проверка копий | MATERIAL-ID, media metadata, ACL |
| Видеоредакторы | Запуск задания/получение результата, монтажная карточка | Сохранение экспортированной версии и её репликация | Новый MATERIAL-ID, derived_from |
| Конструкторы | Встроенные панели/экспорт макетов | Сохранение исходников и экспортов, контроль версий | MATERIAL-ID и provenance |
| Разговорный ИИ | Чат, микрофон, озвучка, подсказки | Только контролируемое хранение аудио/транскриптов и журнал доступа | API gateway, consent, ACL |
| ИИ-летописец | История событий, просмотр видео, карта прогулки и черновик рассказа | Сохранение транскриптов, кадров, треков и одобренных историй | PERSON/EVENT/PLACE/MATERIAL-ID |
| Навигация и карты | Карта, остановки, маршруты и туристический рассказ | Архив треков, картографических экспортов и снимков/медиа | PLACE-ID, EVENT-ID, MATERIAL-ID |
| Supabase | Данные и статусы через безопасный API | Метаданные местоположений, статусы копий и аудит | Backend adapter; прямой доступ браузера ограничен RLS |
| Облачные провайдеры | Пользователь выбирает/просматривает материалы через API | Управление аккаунтами, объектами, копиями и проверками | Provider adapter и registry |

### Два обязательных направления данных

1. **Главный портал → единый каталог → облачные адаптеры.** Пользователь выбирает действие; backend проверяет права, создаёт/обновляет запись каталога, worker передаёт байты провайдерам и проверяет чтение обратно.
2. **Облачная сеть → единый каталог → главный портал.** Статусы провайдеров, доступность копий и ошибки отражаются в медиатеке и личном кабинете без отдельной несогласованной базы.

Облачная сеть не должна становиться самостоятельной медиатекой, а главный портал не должен напрямую писать в облака. Оба интерфейса — разные рабочие поверхности одного ядра.

## 13. Совместимость с текущей инфраструктурой и ограничения запуска

- GitHub Pages обслуживает статические страницы и клиентский интерфейс; он не является местом для приватных файлов, секретов OAuth, постоянных фоновых задач или серверного AI worker.
- Backend KOMAROVA_CORE пока не подтверждён как развёрнутый production-сервис и не подключён к GitHub Pages. Поэтому все новые интеграции в этом реестре имеют проектный/исследовательский статус, если не указано обратное.
- Существующий Supabase project сохраняется без изменений. Не включать новые расширения, buckets, таблицы, Auth, RLS или Edge Functions без отдельного разрешения.
- Google Drive остаётся временным тестом, а не выбранным постоянным провайдером.
- Слабый Windows-компьютер пользователя не должен быть обязательным сервером обработки. Тяжёлые операции выполняются на будущем серверном worker; локальные редакторы остаются необязательным способом обработки.
- Для каждой интеграции предусмотреть fallback: обычная загрузка/просмотр без плагина, если внешний сервис недоступен.
