# Правила папок и постоянной памяти двух проектов

**Статус:** проектное правило, принято к применению для KOMAROVA_CORE; шаблон для второго проекта. Все изменения — только в рабочей ветке соответствующего проекта. В KOMAROVA_CORE не изменять `main`.

## 1. Два независимых пространства

Каждый проект имеет собственную корневую папку/репозиторий и собственную папку `project-memory/`. Не смешивать память, файлы, настройки, задачи, журналы и резервные копии двух проектов.

- Проект 1: `KOMAROVA_CORE`, репозиторий `alexsandrkomarov1-wq/-ArtBukaBot-`, рабочая ветка `core-backend-foundation`.
- Проект 2: имя и путь ещё не предоставлены. Не создавать фиктивный проект и не записывать в него данные. После указания имени/репозитория создать аналогичную структуру.

## 2. Начальная структура KOMAROVA_CORE

Существующие папки и файлы не перемещать и не переименовывать без отдельного согласования. Уже существующие `assets/`, `backend/`, `config/`, `docs/`, `tools/` и другие каталоги сохраняются.

В корне проекта:
- `project-memory/` — постоянная память о самом проекте: текущее состояние, принятые решения, структура, зависимости, следующие шаги.
- `docs/` — спецификации, архитектура и инструкции.
- `tools/` — вспомогательные скрипты и тесты.
- `assets/` — статические ресурсы сайта.
- `backend/` — серверная часть.
- `config/` — примеры конфигураций; реальные секреты сюда не записывать.

Это начальная карта, а не разрешение на массовую перестройку существующего репозитория.

## 3. Какие папки можно добавлять

Новая папка не появляется самовольно. Для каждой новой папки агент сначала предлагает:
1. точное имя и путь;
2. назначение и типы файлов;
3. почему нельзя использовать уже существующий каталог;
4. оценку ожидаемого размера и риска роста;
5. правила доступа, резервного копирования и удаления;
6. влияние на сборку и публикацию.

Владелец утверждает или отклоняет предложение. После утверждения папка добавляется в этот реестр и в `project-memory/PROJECT_STATE.md`. Изменение фиксируется в append-only `docs/AGENT_CHANGE_REGISTER.md`.

**Предварительно разрешены для предложения, но не автоматически для создания:**
- `project-memory/decisions/` — история решений;
- `project-memory/reports/` — отчёты проверок и состояния;
- `project-memory/structure/` — карты структуры и инвентаризации;
- `data/` — только после выбора реального хранилища, схемы доступа и резервного копирования;
- `tests/` — если существующая структура тестов действительно требует отдельного каталога.

Семейные оригиналы, приватные фото/видео, персональные документы, секреты и токены не хранить в публичном Git-репозитории.

## 4. Что означает «память проекта»

`project-memory/` — долговременная память об устройстве и ходе разработки проекта, а не личная память ChatGPT и не база семейных фактов.

Она должна содержать:
- текущее подтверждённое состояние;
- архитектурные и пользовательские решения;
- утверждённую карту папок;
- задачи, ограничения и блокировки;
- последние проверенные коммиты и CI;
- известные размеры репозитория/локальных данных с датой и методом измерения.

Обновление памяти выполняется после существенного изменения проекта. Старые решения не затираются бесследно: изменения решений дополняют журнал, а актуальный снимок обновляется с указанием даты и ссылки на доказательство.

Факты семейной истории (PERSON/EVENT/PLACE/MATERIAL), даты рождения и оригинальные материалы должны храниться в отдельном защищённом архивном хранилище/БД, а не в Markdown-памяти проекта.

## 5. Измерение размера

Не считать размер проекта по числу файлов или по одному показателю GitHub.
Отдельно измерять и показывать:
- размер репозитория GitHub (метаданные GitHub, приблизительно, в KB);
- размер локальной рабочей папки пользователя;
- размер локальных баз данных и вложений;
- размер облачного архива отдельно по провайдерам;
- размер резервных копий.

Каждое измерение: дата/время, путь/источник, метод, общий размер, число файлов, исключённые каталоги. Не сканировать и не загружать приватные данные во внешние сервисы для измерения.

## 6. Правило изменений

Порядок: предложение → решение владельца → создание папки → обновление карты структуры и памяти → запись в журнал изменений → тесты. Нельзя автоматически создавать десятки каталогов «на будущее».

Для двух проектов действует один стандарт, но отдельные карты, журналы и хранилища. Общим может быть только утверждённый UI/код компонентов, не проектная память или семейные данные.
